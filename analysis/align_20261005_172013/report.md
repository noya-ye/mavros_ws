# 飞过目标后停顿分析

数据：rosbag2_2026_10_05-17_20_13，17:20:13.175 至 17:24:14.454（北京时间）。
控制日志：/home/jetson/.ros/log/align_drop_snake_ego_node_11231_1791192026052.log。
配置：src/offboard_core_pkg/config/align_drop_snake_ego.yaml。

## 结论

已确认的直接原因是下视纠偏状态被触发，识别消息随后中断，控制器保持位置直到 15 秒总超时。日志没有显示这些停顿是定位校准。两次触发均发生在估计目标位置刚越过 0.9 米去重边界时。

两次长等待的完整纠偏窗口内，bag 均未记录新的 contour、circle 或 red_cross 消息。触发时仍可使用此前 0.5 秒内的消息，所以控制日志里的 fresh detection 不代表触发后收到新帧。AlignDown 进入时保存当前视觉序号，之后仅处理新序号；触发后没有新帧时不会用触发帧继续纠偏。

## 原因链条

1. AlignDropSnakeEgoTask::tick 只要求 circle 或 contour 消息新鲜且目标估计位置不在去重半径内，便可中断 Snake/EGO。没有连续帧确认，也没有在触发前要求 YOLO 确认目标。stable_frames=2 是到达后的稳定计数，不是触发门槛。
2. 估计目标坐标由当前飞机位置、yaw 和像素偏移 / 500 得到。若轮廓中心偏移、像素比例不准确、相机姿态变化或视觉延迟导致估计坐标漂移，旧目标可能越过 0.9 米边界并被视为新目标。日志明确证明了越界触发，但未证明是哪一种因素导致漂移。
3. detector.py 中不完整轮廓依然返回 contour_center；camera_center_node.py 只检查中心非空便发布。目标离开视野时，被截断轮廓的中心因此仍可能触发纠偏。这是当前代码中与现象相符的风险，bag 没有相机图像，无法确认两次触发帧的实际轮廓。
4. AlignDownTask 在视觉过期后执行 holdPosition 并返回 RUNNING；父任务一直等到 align_down.timeout_s=15 才退出。这是长停顿的直接原因。
5. 超时时仅在能取得新鲜视觉目标坐标时才加入已处理列表。两次超时时视觉已经丢失，无法通过该分支加入目标。第一次恢复后 0.45 秒又触发一次纠偏，证实超时后的重复触发问题。
6. 无 YOLO 目标时仍须先纠偏到 0.12 米误差内，才输出 NO TARGET 并返回。全程 8 次下视纠偏，其中 5 次 NO TARGET、2 次超时、1 次 FIND TARGET 并投放。NO TARGET 不等于未发生纠偏。

纠偏进入时还会锁定 home yaw，完成或放弃后又返回纠偏前的位置和 yaw，所以视觉上可能表现为停住、转一点、往回挪、再继续飞。

## 建议

- 优先增加触发确认：连续可靠检测、完整轮廓有效性、目标坐标一致性；仅修改 stable_frames 不会解决误触发。
- 为纠偏增加独立的持续丢失退出时间，例如 0.5–1 秒内无新帧时放弃当前尝试，并按进入时保存的目标估计位置暂时抑制重复触发。具体阈值需根据相机帧率和识别连续性验证。
- 调整 retrigger_radius_m 只能缓解边界触发。增大到 1.1–1.2 米之前必须确认相邻真实目标间距，否则可能漏掉邻近目标。不能把 0.927 米越界直接等同于半径配置过小。
- 单纯缩短 timeout_s 可以减少等待时间，但也会中断正常纠偏：本次有一次正常纠偏持续约 11 秒。因此应优先区分“仍有识别、正在纠偏”和“持续丢失、悬停等待”。
- 后续记录相机图像或 debug 图、YOLO、任务状态、MAVROS local pose、state、setpoint、battery 和飞控日志，才能判断是否为同一个实物以及第二次等待期间下降的原因。

## 限制与产物

第二次等待期间 FAST-LIO 高度从约 1.1 米降至地面附近；超时后控制日志一直尝试返回先前位置，直到 Ctrl-C。bag 未包含飞行模式和电池数据，无法判断是人为切模式、飞控保护还是其他原因。

Point 视觉消息没有采集时间戳，控制端以接收时刻判定新鲜度；本次无法测量端到端相机延迟。LIO 与 MAVROS ENU 坐标不完全相同，轨迹用于核对运动与时间，不直接代替控制器目标坐标。
